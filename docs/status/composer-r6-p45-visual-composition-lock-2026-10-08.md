# Composer R6-P4.5 — visual composition lock

## 1. Executive verdict

**R6_P45_STATUS = PARTIAL.** The board now packs objects by stable semantic affinity and content density, with measured cluster birth/dissolution and no clipped cards at the three target viewports. It is materially closer to a living monthly inventory. The lightweight vector Clay language remains visibly flatter than the supplied 3D mockup; the required Clay threshold of 3.5/5 is not met. The next step is **CHATGPT_R6_FINAL_CERTIFICATION**, where a human can judge the visual tradeoff. No P4.6 or business phase follows automatically.

## 5. Card density model

Pure presentation projection assigns `SPARSE`, `NORMAL` or `RICH` from the published amount/count, references, occurrence stack and equipped child count. It reads no user label and performs no financial calculation. Density influences simple card height and context footprint; semantic role still determines an appropriate minimum.

## 6. Semantic family model

Stable identity, icon and context template keys assign `DAILY`, `FOOD`, `MOMENTS`, `PERSONAL_CARE`, `SAVINGS`, `PURCHASES`, `HOME` or `OTHER`. These are placement hints, never visible headings. Daily cards remain near Food, moments near each other, and Beauty children stay near their cluster's former area. Identity-based ranking is deterministic, including household-scoped references.

## 7. Layout algorithm

The board first constructs Beauty/Food visual clusters, then orders top-level objects by affinity. A bounded CSS Grid skyline search finds the first unoccupied cell that fits each object's width and height. Different spans break the strict P4 rows; pagination follows available height and reserves a small bottom edge. The geometry is recomputed from the current presentation model and viewport, never saved to a draft.

## 8. Spatial memory

The board records transient DOM rectangles for the active page. A surviving object animates from its previous rectangle; a newborn cluster starts at the centroid of its children; dissolved children start at the former cluster center. `220 ms` repacking and `290 ms` birth/dissolution apply only when motion is allowed. During an active drag, the item list and viewport size are frozen to prevent repacking under the pointer. No database, local storage or free canvas coordinates were introduced.

## 9. Simple cards

Sparse controls use a shorter footprint, while rich controls keep value, habitual reference, count and person badge legible. Card families receive only mild tints. Resting controls are quiet; action buttons remain available on hover/focus. No target simple card has an obviously oversized empty body in the final 1728 screenshot.

## 10. Contexts

Soirée, Week-end, Cadeau and Visite famille retain distinct hero/title/date plus bottom equipment row. Short-stay is wider to host five real components. The Bowling context still renders its published generic `activity` icon because no stable Bowling subtype is available. No orbital satellite layout returned.

## 11. Equipment rows

Socket order, provenance, selection IDs, acceptance and removal remain published and unchanged. Compact illustrated chips stay aligned at the bottom. REST hides empty slots; the selected context offers at most one primary `+`. A row may scroll horizontally rather than expand the parent uncontrollably.

## 12. Clusters

Beauty and Food remain presentation-only groupings of independent objects. The shelf, miniature spacing, `+N` and opening affordance read separately from a parent context's equipment row. Child totals are not fabricated. A cluster appears only at three or more children, with stable IDs and no duplicate top-level child. The overlay now forgets its open state after dissolution, so Undo recreates the capsule without reopening the dialog.

## 13. Saving

The piggy bank, green surface, published amount and progress preserve the savings silhouette. Saving is protected only when published capabilities require it. `SAVING_DISPLAY_LABEL_GAP` remains: the synthetic fixture publishes “Synthetic adjustable saving”; the UI does not invent a new finance label.

## 14. Library

At roughly 284 px, the Library remains narrower than the board. Section headings, backgrounds, borders and item shadows are quieter. Search, `/`, arrow navigation, Enter, click and drag remain available. The board still dominates the width.

## 15. Palette

The equipment belt uses a softer surface and separators; `AVANT`, `MOMENT`, `REPAS` and travel groups stay readable. Horizontal scroll and multiple-route choices remain accessible. In the 1728 selected scene, it does not cover the board or pagination.

## 17. Clay

The shared vector frame uses top-left lighting, layered gradient stops, small highlights and contact shadows. Groceries, short-stay and family gain side/overlap geometry; the gift improvement from P4 remains. No raster asset, expensive blur or heavy per-icon filter was introduced. The visual result remains a simplified vector illustration system rather than the mockup's sculpted 3D: **Clay 3/5**, below the mission threshold.

## 18. HUD

One horizontal capsule emphasizes Fin de mois, then Sans changements, Impact, Objectif and Marge. Separators are subtle; color semantics are unchanged. The synthetic scenario still shows unknown values as `—` and the published `889,00 €` reference. No UI finance arithmetic was added.

## 20. Unknown

Unknown stays unknown rather than becoming zero. Sparse unknown cards use a small amber dot and explicit “Budget à préciser” wording. The screenshot `r6-p45-unknown.png` records a fixture with that state.

## 21. Protected

Protection follows actual capabilities/flexibility. A protected drag exposes a lock and refuses trash without a command or server write. The synthetic protected screenshot and browser assertion record that refusal. Saving is not automatically protected.

## 22. Person badges

The published person label is a quiet rounded microbadge beside the relevant object title; it remains visible without dominating amount or icon. The fixture shows Adrien on Café. No person inference from free text was introduced.

## 23. Hover/focus

Hover elevation is one pixel over 145 ms with no layout jump. Focus-visible is a consistent 3 px violet outline across board, Library, palette and header controls. Keyboard focus on a cluster measured a 3 px outline in Chrome. The context's selected border remains distinct from keyboard focus.

## 24. Motion

FLIP-style DOM animations preserve object continuity across packing, cluster birth and dissolution, with stable React keys. Animation uses only transform and opacity. The overlay continues to use native dialog focus management and Escape; dissolved-child focus returns to a surviving object.

## 25. Reduced motion

The existing workspace-wide reduced-motion CSS disables transition/animation effects. New Web Animations explicitly check `prefers-reduced-motion: reduce`; browser emulation found zero running board animations after selection. Hover and selection remain understandable without motion.

## 26. Accessibility

Browser smoke covered keyboard focus, popover Escape/focus return, dialog opening/closing, equipment alternatives, protected refusal and surviving-child focus after dissolution. Visible outline is confirmed. Semantic HTML buttons, native dialog and popover remain in use. Human contrast and small equipment-label readability still deserve final certification; no critical accessibility fault was observed in the scripted paths.

## 34. Remaining gaps

1. `CLAY_TARGET_GAP`: the vector system is recognisable but below the mockup's sculpted volume and the mission's 3.5/5 Clay threshold.
2. `MISSING_VISUAL_IDENTITY`: Bowling publishes only the generic `activity` key; an exact icon requires a stable published subtype.
3. `SAVING_DISPLAY_LABEL_GAP`: the synthetic fixture's savings name is technical and no trusted replacement label is published.
4. `COMPARE_DELTA_UNPUBLISHED`: no certified delta is available to show in the UI.
5. Human contrast/readability review is still needed for tiny equipment labels and muted secondary metadata. No critical failure surfaced in scripted Chrome checks.

These are precise certification inputs, not an instruction to start another implementation phase.
