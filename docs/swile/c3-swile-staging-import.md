# C3 — Swile staging importer

The Swile adapter reads the supplied workbook and the certified A2/A3 oracle. It verifies all 200 purchase rows against A2/A3 and passes a provider-neutral DTO to `importBenefitSnapshot`. The generic importer handles source identity, gross, ownership, funding, wallet ledger, timing, channels, classifications and pilot visibility. It has no Swile-specific ownership or amount branch. The actual merchant is retained separately from the Uber Eats channel.

The source workbook uses namespace-prefixed OOXML that the repository's ExcelJS version cannot read. The adapter uses a small `openpyxl` bridge to extract only the required sheets in memory. Workbook content and the resulting DTO are never committed. The source file's exact byte SHA-256 is the batch file hash. IDs are derived from household, source, instance, snapshot, fingerprint, occurrence and semantic role. The one repeated fingerprint keeps ordinals 1 and 2.

Run `scripts/check-c3-swile-staging.mjs` with the raw workbook, FINAL MASTER workbook and a private JSON report path as its three arguments. Set `SWILE_PYTHON` to Python with `openpyxl` and `PGLITE_MODULE_PATH` to a local PGlite `dist/index.js`. The harness creates two disposable PostgreSQL databases. It applies the two historical PurchaseEvent migrations, then C1, C2 and the C3 event semantic context migration. Existing A3 Operation IDs and their certified bank amounts are seeded only as local reference fixtures. Generic merchant, category, subcategory and Need IDs are also seeded as local references. No source workbook rows or personal bank data are written to the repository.

The C3 migration stores merchant, category, subcategory, Need and generic `semantic_purpose` on PurchaseEvents, including mixed purchases whose existing Operation remains the economic owner. C2's pilot projection reads those purchase assertions. The `economic_component_classifications` axes remain on the effective owner. No gross is copied to the native purchase component, no Operation bank amount changes, and no FOOD engine changes.

An identical workbook returns `EXACT_REPLAY` with zero semantic writes. A changed file hash for the same source instance returns `REQUIRES_RECONCILIATION`; the importer does not silently activate a corrected snapshot without provider-native correction identity. The staging report maps each of the 200 source rows to its external ID, PurchaseEvent, effective owner, gross quality, funding, generic classification, A2 verdict and A3 treatment. It remains outside Git because it contains merchant/source details.

The local replay proves table constraints and deterministic business rows but does not claim a full Supabase reset: the repository lacks the entire historical base DDL. Live C6 prerequisites include applying C1, C2 and C3 with human-reviewed migration validation, resolving the 17 merchant references marked `TO_CREATE` in the source workbook, and rechecking live reference identities and source revisions before import. Source corrections beyond byte-identical replay require a later reconciliation policy.
